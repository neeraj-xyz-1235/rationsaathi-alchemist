# Frontend Plan — React (M + A)

The detailed UI spec is the "frontend context" section of context.txt (accessibility, screens,
validation rules, definition of done). It still applies. The VISUAL reference is the team mockup
image (header, 3 screens, component library), described in §2 so it lives in the repo.
This file covers: who builds what, the theme, routes, state, the API hookup, login/signup,
and the map placeholder.


## 1. Changes from context.txt and the mockup (agreed for the whole team)

  1. NO arithmetic in the frontend. The mockup's app structure lists utils/calculator.js and
     utils/receiptParser.js; we do NOT build those. Review and Report call POST /api/calculate,
     and receipt reading calls POST /api/receipt/parse (plan_backend.txt §2). Reason: one source
     of truth, which is tested Python with exact integer math.
  2. Validation uses zod schemas (src/validation/) for ALL forms, including family, rules,
     records, login and signup. No hand-written validation.js.
  3. Routing uses react-router-dom, because we now have more than 3 screens (§4).
  4. Translations are split per screen to avoid merge conflicts (§5).
  5. Report sentences are built from backend codes using translated templates (§6).
  6. The mockup uses October 2024 dates. The demo uses September 2026, an ended period
     (plan_overview.txt §6).
  7. The mockup's "Household reference" placeholder says "e.g. Ration Card Number". Change it to
     "e.g. Home – September" with the hint "Don't enter card or ID numbers".
  8. The mockup's rules table has only "Quantity per Member". Add a "Per member / Per household"
     choice (the backend supports both).
  9. Checking a ration works WITHOUT an account. Login is only needed to save cases and create
     share links.
 10. Monthly tracker (/tracker, login required) replaces "My saved checks": every saved case is
     one month, listed with its balance. (§11.2)
 11. Balance panel on the report: how much of the entitlement is recorded vs remaining, e.g.
     "7 of 10 kg". Numbers come from the API's `balance` block; the frontend does no maths. (§11.1)
 12. Complaints page (/complaints): a static list of official portals + a neutral summary to copy.
     We never file anything and say so. (§11.3)
 13. "Email me this report" button on the report, sent to the account email only. (§11.4)

## 5. Shared contracts inside the frontend

CaseContext (M owns it; A's wizard reads and writes through it):
  caseData   EXACTLY the Case object in plan_backend.txt §2.1
  result     the /api/calculate response
  setCase, resetCase
  - Save caseData to localStorage as a draft on every change (wrapped in try/catch), so a
    refresh, or a detour through /login, doesn't lose the user's input.
  - Clear the draft on logout and on "Start over". People often share phones.
  - Quantities stay STRINGS from the input field to the API. Never Number() them.
  - New rule/record ids: crypto.randomUUID().

API client (M, ready by T+1:15 so A can use parseReceipt):
  - All URLs are RELATIVE: fetch('/api/...'). Vercel and the Vite dev server forward them to the
    backend (plan_deployment.txt §5). That keeps the login cookie first-party. Never hard-code
    the Render URL.
  - Send credentials: 'same-origin' and Content-Type: application/json on every request.
  - Functions: calculate, parseReceipt, listCases, saveCase, updateCase, deleteCase, createReport,
    getReport, getNearbyShops, getTracker, nextMonth(caseId), emailReport(reportId, lang),
    listGrievances / saveGrievance (optional), auth.signup, auth.login, auth.logout, auth.me
  - Error responses come as { error: { code, fields?, retry_after_s? } }. Throw an ApiError with
    those fields, and the pages translate the code with t('errors.' + code).
  - 401 on a protected call → clear the user in AuthContext and go to /login?next=<current path>.
  - VITE_USE_MOCKS=true → return the mock JSON after a 400 ms delay (auth mock: any email +
    "password1234" logs in).
  - If a request takes >5 s, show "Starting the server, this can take up to a minute"
    (the Render free tier sleeps when idle).

i18n:
  t('entry.addRecord'), t('report.sentence.shortfall', { item, received, expected, diff, unit, period })
  Missing key in hi/mr → fall back to English + console.warn. CI catches it anyway.
  Each person writes en/hi/mr for their own file. A first draft via a translation tool is fine,
  but a Hindi/Marathi speaker on the team reviews it before freeze.


## 6. Report sentence templates (M) — neutral, no banned words

  shortfall        "Confirmed records for {item} total {received} {unit} against an expected
                    entitlement of {expected} {unit} for {period}, a difference of {diff} {unit}.
                    The reason for this difference has not been established."
  no_difference    "Confirmed records for {item} total {received} {unit}, which matches the
                    expected entitlement of {expected} {unit} for {period}."
  above_expected   "Confirmed records for {item} total {received} {unit}, which is {diff} {unit}
                    more than the expected entitlement of {expected} {unit} for {period}."
  unclear/PERIOD_NOT_ENDED  "So far, confirmed records for {item} total {received} {unit} of an
                    expected {expected} {unit}. The period ends on {end}, so this may change."
  unclear/excluded "{n} record(s) for {item} were not included: {reasons}. Please review them."
     reasons:  PENDING_NOT_CONFIRMED "not yet confirmed" | MISSING_DATE "no date entered" |
               OUTSIDE_PERIOD "dated outside the period" | UNIT_MISMATCH "unit doesn't match the rule"
  late             "{n} distribution(s) of {item} are dated after the due date of {due_by} that you entered."
  unrecorded       "{n} receipt(s) for {item} were added but not confirmed, so they are not in the total."
  unmatched        "{item}: no entitlement rule was entered for this item, so it was not compared."
  evidence         no_receipt=true → "No receipt (stated by user)"; nothing given → "No evidence provided"
  footer           "This report compares recorded quantities with the rules you entered. It does
                    not establish the cause of any difference."
  balance (per phase; {remaining} etc. come straight from the API's balance block):
    ongoing, remaining > 0   "{remaining} {unit} of your {expected} {unit} for {item} is still to be
                              collected this period ({percent}% recorded so far)."
    ended, remaining > 0     "{remaining} {unit} of the {expected} {unit} entitlement for {item} was not
                              recorded as collected in this period. This does not say why."
    remaining = 0, over = 0  "The full {expected} {unit} for {item} has been recorded."
    over_by > 0              "{over_by} {unit} more than the entitlement has been recorded for {item}."
    carry note (always)      "Whether unused ration can be collected later depends on the scheme's own
                              rules, which this tool does not assume. Please check with your local office."
  The email in plan_backend.txt §6.9 repeats the shortfall / no_difference / above_expected
  sentences. If you change them here, tell N in the same PR.
  The parser issue codes (plan_backend.txt §2.3) also each need a sentence (A, in entry.js).


## 7. Login + signup with zod (M)

Schemas (src/validation/auth.js). They MUST mirror plan_backend.txt §2.5. If one side changes,
the other changes in the same PR. Error messages are i18n KEYS, shown via t(error.message).

  email:        z.string().trim().toLowerCase().max(254, 'auth.emailTooLong').email('auth.emailInvalid')
                (zod v4 also has z.email(); use whichever the installed version documents)
  password:     z.string().min(10, 'auth.passwordTooShort').max(128, 'auth.passwordTooLong')
  displayName:  z.string().trim().max(50, 'auth.nameTooLong').optional()
  loginSchema:  { email, password: z.string().min(1, 'auth.passwordRequired') }
                Login only checks "not empty". Never tell someone their old password is "too
                short"; the server decides.
  signupSchema: { email, password, confirmPassword, displayName }
                .refine(d => d.password === d.confirmPassword,
                        { path: ['confirmPassword'], message: 'auth.passwordsDontMatch' })

Forms: react-hook-form + zodResolver(schema), mode 'onBlur', errors shown under each field
(red text + ! icon, as in the mockup) and announced with aria-describedby / aria-invalid.
After a server error, map error.fields onto the form with setError so server-only checks
(PASSWORD_TOO_COMMON, EMAIL_UNAVAILABLE) appear in the same place.

UX + security details:
  - Inputs: type="email" autocomplete="email"; password autocomplete="current-password" (login)
    / "new-password" (signup); a show/hide password toggle (eye icon, with a label). Never block paste.
  - Hint under the signup password: "At least 10 characters. A short sentence works well."
  - Disable the submit button while the request is in flight (no double submits).
  - INVALID_CREDENTIALS → "Email or password is incorrect." Never say which one was wrong.
  - RATE_LIMITED → "Too many attempts. Please try again in {minutes} minutes." (from retry_after_s),
    and disable the button until then.
  - After login: navigate to ?next= ONLY if it starts with "/" and not "//" (prevents an open
    redirect to another site); otherwise go to /.
  - The session lives in an HttpOnly cookie that JavaScript can't read. Never store tokens or
    passwords in localStorage/sessionStorage, and never console.log form values.
  - AuthContext calls GET /api/auth/me once on app start to know whether someone is logged in.
  - Report page: "Save" / "Get share link" when logged out → "Log in to save this check" →
    /login?next=/report. The draft survives through localStorage, so the user loses nothing.
  - Share link screen: "Anyone with this link can view this report."


## 8. Map placeholder — nearest ration shops (A) — PLANNED FEATURE

  Page /shops + the Home banner card. Built so that real shop data can be plugged in later
  without UI changes.
  - Leaflet + react-leaflet. Load the map component with React.lazy so its JS doesn't slow the
    home page. Import 'leaflet/dist/leaflet.css'. Vite breaks Leaflet's default marker icon, so
    import the marker PNGs explicitly and set L.Icon.Default.
  - Tiles: https://tile.openstreetmap.org/{z}/{x}/{y}.png with the attribution
    '© OpenStreetMap contributors' linked to openstreetmap.org/copyright. The attribution is
    REQUIRED by OSM's licence. OSM's public tiles are fine for a light prototype; production
    needs a tile provider.
  - Default view: India, centre [22.5, 79.0], zoom 5. The map box is 360 px tall (240 px on mobile).
  - "Use my location" button: call navigator.geolocation ONLY when clicked, with a line
    explaining why. If granted, centre there (zoom 13) with a "You are here" marker. If denied,
    keep the default view and show a calm message. Don't store the location.
  - Call getNearbyShops(lat, lon). The backend returns status "planned" and an empty list, and
    the page shows an Alert (info): "Coming soon: we're collecting verified ration shop
    locations. No shops are shown yet."
  - NEVER show sample or made-up shop pins. A fake location could send someone to the wrong
    place.
  - Below the map, a text version for screen readers: "Map of your area. Shop locations are
    not available yet."
  - Strings go in i18n/shops.js (en/hi/mr).

## 11. Phase B features (balance, tracker, complaints, email)

Build these after Checkpoint 2, in the order of §11.5. Each has its own cut-list position
(plan_overview.txt §8).

### 11.1 Balance panel on the report (M)
  - Under the 3 summary cards, per item: ProgressBar whose width is `percent_used` from the API
    (visually capped at 100%), with the text always beside it: "7 of 10 kg recorded (70.0%)".
  - Below it, one sentence from the balance templates (§6) chosen by `phase` and the numbers, then
    the carry note in small grey text.
  - Example (ongoing, 7 of 10 kg): "3 kg of your 10 kg for Rice is still to be collected this
    period (70.0% recorded so far)."
  - Never compute remaining or percent in the frontend. Read the `balance` block.
  - Colours: green for the recorded part, grey for the rest. Not amber, not red. It prints
    properly in black and white because the text carries the meaning.

### 11.2 Monthly tracker /tracker (M)
  - Logged out: a card explaining the tracker with Log in / Sign up buttons, plus "or continue
    without an account".
  - Top bar: title, a household selector (only when there is more than one household_ref), and
    "Start next month". That button calls nextMonth(latest case of the selected household), then
    opens /check with the new case loaded (rules and members already filled in, no records). A
    409 shows "This month already exists" with an Open link.
  - MonthCard list, newest first:
      period label (month name + year, Intl.DateTimeFormat with locale en-IN / hi-IN / mr-IN and
      numberingSystem 'latn'), phase badge (Ongoing / Ended, text + icon),
      one row per item: name, MiniBar, "14 of 20 kg · 6 kg remaining" (all values from the API),
      LabelBadge for each label, buttons: Open (edit in the wizard), View report, Delete (confirm).
  - Empty state: "No saved months yet. Check a ration and press Save."
  - The balance sentence rules in §6 apply here too. Never say why anything is below the
    entitlement. Carry-over note shown once at the bottom of the page.
  - Optional (cut first): a compare table, rows = items, columns = months, cells = percent_used.
    Plain HTML table, no chart library.
  - Optional (cut first): "My complaint notes" per month card, using the grievance endpoints.

### 11.3 Complaints page /complaints (A)
  - Purpose: show where a person can raise a query or grievance. We never file anything, and the
    page says so in an Alert at the top: "RationSaathi is an independent tool. It is not a
    government service and cannot submit a complaint for you."
  - Neutral intro: "A difference in a report does not, by itself, say what caused it. If you want
    someone to look into it, these official channels can review your records."
  - Three step cards: 1) Get your report (buttons: Print, Email me this report, or "Generate a
    report" if none exists), 2) Keep your evidence (receipt numbers, photos, notes), 3) Choose
    where to raise it (below).
  - Data: src/data/complaintLinks.json, an array of
      { key, scope: "national" | "state", state: null | "Maharashtra", kind: "portal" | "helpline",
        name: {en,hi,mr}, description: {en,hi,mr}, url, phone, last_verified: "YYYY-MM-DD" }
  - A state selector (default = national only), remembered in localStorage (try/catch). It shows
    the national entries plus those for the chosen state.
  - Each entry is a card: name, description, domain shown in text, an "Open official site ↗" link
    with target="_blank" rel="noopener noreferrer" and "(opens in a new tab)" text. Helplines get
    a tel: link. Never embed a portal in an iframe.
  - STARTING POINTS, NOT FACTS. I could not open these live while writing the plan. Whoever builds
    the page opens every URL and checks every number in a browser, and sets last_verified:
        national:    National Food Security Portal (nfsa.gov.in)
                     CPGRAMS public grievance portal (pgportal.gov.in)
                     Dept. of Food & Public Distribution (dfpd.gov.in)
                     national toll-free PDS helpline(s): 1967 and 14445 are commonly cited, confirm
        Maharashtra: the state food, civil supplies and consumer protection department site
                     (e.g. mahafood.gov.in) and its helpline, confirm
    Don't add an entry without opening it. Add more states only if someone can verify them.
